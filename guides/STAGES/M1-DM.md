# M1 실무자 DM — 「DM 시작하자」 · 실무자 회신은 DM 탭이 (오케스트레이터 + DM 탭)

> `roles/오케.md` 「사용자 신호」가 여기를 가리킨다. 질문 글의 규약·순서는 `guides/INTERVIEW.md`, 형식은 `docs/interview/TEMPLATE.md`. **표준 구조: DM 전담 탭**(`roles/DM.md`)이 실무자 회신을 받아 다음 질문과 누적 요약을 맡고, 오케는 그동안 다른 일을 한다. F1 로그: 오케가 DM 1회에 3~7분(38~52% 가 PROBLEM 통째 재생성)을 쓰는 사이 실무자 답은 6~8초에 와서 4~359초 기다렸다 — 즉석으로 만든 DM 보완 탭은 한 턴 38~73초로 돌았다. 공유는 **파일**(`docs/interview/`)이고 탭끼리 직접 부르지 않는다. (`codex queue` 가 사전 체험에서 되면 「DM 탭이 오케에 요약 알림」 용도로만 선택.)

## 오케스트레이터 몫

- **「DM 시작하자」** — 사용자가 브리핑을 두고 오케와 몇 번 이야기한 뒤 친다. 「DM 시작하자, 단위부터 확인해」처럼 **의도를 붙이면** 그 의도를 질문 1 의 맨 앞에 두고 `decision` 에 「제안: 사용자」로 남긴다. **그 턴에 보낼 글을 가장 먼저**: `docs/interview/M1.md` 「질문 1」(오프닝 + PROBLEM 15절 맨 위에서 고른 가장 깊은 좌표 질문 2~3개, 해법 단어 없이 — 순서는 배경 → 사용자 → 제약 → 성공 기준 → 우선순위, 사소한 것에서 구체로. 「정답을 달라」는 질문 금지)과 `docs/interview/보낼글.txt` 를 쓴다. 이어 `docs/STRATEGY.md`(문제 쪽 4항목: 진짜 문제 가설 · 브리핑 이후 바뀐 것 · 인터뷰로 깨 볼 가정 · 해법 보류함 — 해법은 보류함에만) 첫판을 쓴다. 사용자 메모장(`docs/MEMO.md`)은 읽지 않는다 — 사용자가 내용을 붙여 넣으면 가설 입력으로 받아 STRATEGY 2번에서 짚는다(메모는 정답지가 아니다: README·데이터·실무자 답과 어긋나면 근거를 들어 짚는다). 사례: `docs/research/현장사례-*.md` 가 끝났으면 사례마다 PROBLEM 15절에 질문 후보 한 줄(`[사례:파일]`)과 STRATEGY 3 「깨 볼 가정」으로 올린다. 사례는 실무자가 확인해야 사실이다 — 1~14절에는 넣지 않는다. 질문 1 에 사례 근거 질문을 1개까지 넣는다(`guides/INTERVIEW.md` 「사례 근거 질문」, 예/아니오 유도 금지).
- **DM 탭 안내** — 같은 응답에서 DM 탭을 연다(DM 탭은 시작 때 README 원문 · PROBLEM 전체 · STRATEGY · 데이터 프로필 · 현장 사례를 한 번 읽는다 — `roles/DM.md`): `새 탭 → codex → /model 표준 등급 · medium(KICKOFF 세션 편성 표) → 「roles/DM.md 읽고 그대로 해」 → 탭 이름 DM`. 마지막 줄 `다음 입력(DM): roles/DM.md 읽고 그대로 해` + `그다음(DM): (DM 의 실무자 답을 그대로 붙여넣기)`. 이후 실무자 답은 **DM 탭에** 붙여넣는다(오케 탭이 아니다).
- **오케는 DM 이 도는 동안 쉬지 않는다**(10:12~10:40) — 브리핑 후속 질문 · 현장 사례 흡수 · 리서치 결과 반영 · 방향과 무관한 PLAN 초안, 그리고 **문제 확정 전에 미리 짤 수 있는 코드**를 서브에이전트로 병렬로 돌린다(「병렬로 띄우고 기다리지 않는다」). 미리 짤 코드는 데이터 읽기 · 전처리 · 이상 탐지 · 화면 뼈대까지이고 **업무 규칙은 확정 뒤에 넣는다**. 사람의 중계와 DM 탭 산출물은 `guides/STAGES/시간표.md`. **DM 이 도는 동안 발견한 업무 질문(데이터와 말이 어긋나는 곳 · 리서치 「실무자에게 확인할 것」 · 설계에서 막힌 업무 갈림길)은 `docs/interview/질문후보.md` 에 한 줄**로 남긴다 — DM 탭이 회신 턴마다 읽는다(오케·서브에이전트가 쓰고 DM 탭은 반영 표시만). 미리 짜는 전처리 서브에이전트는 데이터 구조·이상 결과를 `docs/research/데이터프로필.md` 에 쓴다. DM 상황이 필요하면 **`docs/interview/요약.md` 만 읽는다**(대화 원문 `M<n>.md` 를 매번 읽지 않는다). 오케는 `M<n>.md`·`보낼글.txt`·`요약.md` 를 고치지 않는다 — 이 셋은 DM 탭 소유(질문 1 만 오케가 쓴다).
- **PROBLEM·STRATEGY 는 매 턴 고치지 않는다.** 오케가 「문제 확정」 때 `요약.md` 를 한 번에 PROBLEM 해당 절에 `[답변N]` 으로 반영한다(`M1-확정.md`). 바뀐 줄은 취소선으로 남기고 통째 재작성하지 않는다.
- 사용자가 DM 요약을 물으면 「DM 탭 요약을 읽어 줘」가 아니라 오케가 `요약.md` 를 읽고 핵심만 답한다. DM 탭이 ㉠ 이 찼다고 알리면 오케가 `problem_check.py` 와 관문(`guides/INTERVIEW.md` ㉠·㉡·㉢)으로 확인한다.

## DM 탭 몫 (`roles/DM.md` 가 정본 — 여기엔 요지만)

실무자 회신이 오면 **먼저** 「답변 N」 원문을 `docs/interview/M<n>.md` 에 덧붙이고 → 다음 「질문 N+1」(이미 받은 답은 안 묻는다 · 업무 질문만) 을 같은 파일과 `보낼글.txt` 에 쓴다 → 그 다음 **답변 분해**를 `docs/interview/요약.md` 에 바뀐 줄만 덧붙이거나 고치고(규칙 · 숫자 · 합의 · 미확인 · 숨은 사실 점검표 · 관문 상태) → 턴을 짧게 끝낸다(목표 1분 안팎). 응답은 5줄 안: 이번 질문이 무엇을 묻는지 한 줄 + ㉠ 미충족 번호 + `다음 입력(DM): (DM 의 실무자 답을 그대로 붙여넣기)`.

## 업무 갈림길 vs 기술 갈림길

답을 분해하다 갈림길이 나오면 **업무**(무엇을 먼저 보나 · 무엇이 쓸 만한가 · 읽는 순서)는 사용자에게 고르게 하지 말고 **다음 실무자 질문으로** 올린다(DM 탭 몫). **기술**(저장 · API · 화면 수 · 라이브러리)은 오케가 정하고 `decision` 으로 남긴다. 페르소나는 개발 방법에 답하지 않는다.
