# INTERVIEW.md — 실무자 인터뷰 규약 (4단 루프)

> 원칙: 표면 요구(want)를 그대로 만들지 않는다. 원인(pain)을 캐고, 이해를 **서면으로 합의**받고, 중간·최종에 **실물로 확인**받는다. 대화는 짧은 질문 여러 번이 긴 질문 한 번보다 낫다.
> 보낼 원문과 회신은 `docs/interview/M<n>.md` 한 파일에 순번으로 쌓는다 — 규약은 `COMMS.md`.

## 질문 글과 회신 루프 (`docs/interview/M<n>.md`)

- 표기는 「질문 N / 답변 N」. 질문 글은 **사람답게**: 존댓말 메신저 구어체, 보고서·요약 말투 금지, 앞 답변의 말을 받아 시작(「아까 ~라고 하셨는데요」), 상대가 쓴 용어 그대로. 번호 목록은 허용, 굵은 글씨·소제목은 쓰지 않는다. 예: 「말씀 감사합니다. 아까 월말에 몰린다고 하신 부분이 마음에 걸려서요, 다음과 같은 사항이 궁금해요. 하나씩 답해주시면 감사드릴게요. 1. ~ 2. ~」
- **회신은 DM 탭이 받는다(`roles/DM.md`) — 보낼 글 먼저, 짧게**: ① 「답변 N」 원문 기록 ② 「질문 N+1」(쓰기 전 직전 답변 재독, 이미 받은 답은 안 묻는다 — `PROBLEM.md` 15절 맨 위 「답이 오면 가장 많이 바뀌는 것」에서 고른다) + `docs/interview/보낼글.txt` 덮어쓰기 ③ **답변 분해 → `docs/interview/요약.md`**(바뀐 줄만) ④ 커밋 ⑤ 5줄 안 응답. `PROBLEM.md`·`STRATEGY.md` 는 매 턴 고치지 않고 오케가 「문제 확정」(설계는 「설계 확정」) 때 요약을 한 번에 반영한다. 질문 순서는 **배경 → 사용자 → 제약 → 성공 기준 → 우선순위**, 사소한 것에서 구체로. **「정답을 달라」(「뭘 만들면 좋을까요」「해법을 알려 주세요」)는 묻지 않는다** — 업무를 묻고, 개발 방법은 오케가 정한다. 업무 갈림길(무엇을 먼저 보나 · 무엇이 쓸 만한가 · 읽는 순서)은 실무자에게 묻고 사용자에게 고르게 하지 않는다.
- **답변 분해** (③): 답변의 문장마다 **사실·규칙·숫자·감정·용어·정정** 중 무엇인지 가른다. 갈라진 것을 `요약.md` 에 `[답변N]` 태그로 넣고 오케가 `PROBLEM.md` 해당 절로 옮길 때(「문제 확정」)(바뀐 줄은 지우지 않고 취소선 `~~옛 내용~~ → 새 내용 [답변N]`), 어느 절에도 안 들어가는 문장은 요약 「미확인」에 올리고 15절의 새 빈틈이 된다.
- **답변 2개마다 세 층 다시 보기**: 넓게(1절 `[?]` 가 줄었나) · 엮어(2절 「말하지 않은 요구」에 근거가 붙었나, `[짐작]` 이 남았나) · 먼저(14절 모퉁이 너머) — 결과를 설명 다섯 칸 앞에 한 줄로 쓴다.
- **설명 다섯 칸**(DM 탭은 새로 안 것 한 줄 + 미충족 번호만, 다섯 칸은 오케가 단계 전환 때 요약을 읽고 말한다 · 순서는 같다): 새로 안 것 · 흘린 말·감정 신호 · 말과 데이터가 어긋나는 곳 · PROBLEM 빈 절 · 다음 앵커까지 남은 시간.
- **관문 원리 (문제·설계·피드백 공통)**: 관문은 세 층이다. **㉠ 꼭 받기**(실무자의 명시 답이 있어야 충족) · **㉡ 물어보면 충족**(질문을 보낸 기록이 `M<n>.md` 에 있으면 충족 — 답이 「모른다」여도 된다) · **㉢ 「모른다·확인해 봐야」 처리** — ㉠ 이든 ㉡ 이든 실무자가 그렇게 답하면 ① `요약.md` 「미확인」에 적고 ② 가정 하나를 세워 `decision` 으로 남기고(PROBLEM 줄에는 `[가정:D번호]`) ③ 그 가정을 README 「안 된다」 또는 서술형 소재(`docs/QNA.md`)에서 밝히기로 적으면 **닫힌 것**으로 본다. 같은 질문을 두 번 묻지 않는다(F1: 「확인해 봐야」 항목이 영원히 안 차서 DM 8번에 미충족이 15개→12개로만 줄었다). **목표: DM 4~5왕복에 닫는다.** DM 탭은 매 턴 `요약.md` 「관문 상태」에 **㉠ 의 미충족만** 짧게 보인다. 넘어가기는 사용자의 신호이고, 근거(`[답변N]`·`파일:행`·명령 출력)를 못 대면 미충족이다.
- **문제 확정 관문** (M1 — `docs/interview/M1.md`)
  - ㉠ 꼭 받기 6개: ㉠1 **진짜 문제 한 문장**에 실무자 명시 동의(되말하기에 「네 그거예요」 — 「절반은 맞는데요」면 아직) · ㉠2 **결과를 받는 사람과 그 사람이 다음에 하는 일** · ㉠3 **데이터 이상 처리 규칙** — 결측·중복·단위·기간 경계마다 규칙이 실무자 확인 또는 ㉢ 처리, 아래 숨은 사실 점검표 8개가 「확인됨 / 가정 / 해당 없음」 · ㉠4 **만들 범위(MUST)** 동의 — README 요구 문장이 전부 9절에 ID 로 있고(README 의 「해야」「필요」「제출」 문장 수와 대조) MUST 마다 근거 · ㉠5 **안 할 것과 이유** 동의 · ㉠6 **서면 합의문(아래 ②)을 보내 명시 확인** — 성공 기준(지금 값 → 목표 · 측정처)이 그 안에 있다. 받은 시각을 PROBLEM 확정 시각 옆에
  - ㉡ 물어보면 충족 5개: ㉡1 걸린 사람(결재·하류·감사) · ㉡2 건드리면 안 되는 흐름 · ㉡3 모퉁이 너머 2개 이상(14절) · ㉡4 비용·기준선 숫자와 측정처 · ㉡5 최근 에피소드 1개(언제·누가·무엇을·얼마나 걸렸나)
  - 기계 항목(`python3 tools/problem_check.py` — ㉠ 판정을 돕는다): 빈 절 0 · 출처 태그 없는 줄 0 · `[짐작]` 은 `[가정:D번호]` 가 붙으면 허용 · 1절 `[?]` 0(남으면 15절로 옮기고 MUST 에 영향 없다는 근거) · 숨은 사실 점검표 「아직」 0. 나머지 판단은 오케가 근거를 대며 한다.
- **설계 확정 관문** (M2 설계 DM — `docs/interview/M2.md`) — 구조는 위 원리와 같고 반영처가 PLAN·ARCHITECTURE 다(문제가 바뀌면 PROBLEM 도 취소선). ㉠ 이 차고 자체 점검이 차면 구현 직전 평가(모드 1)를 서브에이전트로 띄우고, 평가 지적 처분까지 끝나면 「설계 확정해도 됩니다」를 권한다.
  - ㉠ 꼭 받기 4개: ㉠1 결과물 모양·사용자 흐름 동의(받은 사람이 **다음에 하는 일**까지) · ㉠2 안 하는 것(PROBLEM 10절 + PLAN 7절 자를 순서의 선택 요구) 동의 · ㉠3 실무자 판단이 필요한 데이터 처리 규칙(PLAN 4절) 확인 · ㉠4 **설계 합의문**(무엇이 나오나 · 사용자 흐름 · 경제적 효과 · 안 하는 것 · 실무자가 정한 규칙 — 한 덩어리로 복사해 갈 수 있게)에 명시 확인, 받은 시각을 PLAN 에
  - ㉡ 물어보면 충족 3개: ㉡1 리서치 「실무자에게 확인할 것」 중 큰 것 2~3개를 물었다 · ㉡2 경제적 효과 숫자(M1 기준선 → 목표 · 측정처)를 보였다 · ㉡3 건드리면 안 되는 흐름(문제 관문 ㉡2)을 설계가 건드리지 않음을 확인 질문에 넣었다
  - 자체 점검 6개(실무자 답 불필요 — 오케가 근거를 댄다): ① PLAN 1~9절·ARCHITECTURE 1~11절 빈 절 0(화면이 없으면 9절은 「없음」과 이유) · 모듈 2~4개 · 모듈마다 입출력 예시가 PROBLEM 5절 실제 데이터 모양 · 데이터 계약(7절)과 규칙 파일(8절) ② PLAN 2절에 요구 ID 전부 — MUST 마다 모듈·테스트 이름·검증 명령 ③ 결정론/AI 경계와 AI 실패 폴백(ARCHITECTURE 5절, 제품 안 AI 호출이 없으면 「없음」과 이유) ④ 사용자가 구조를 3줄로 설명할 수 있다(설명 못 하면 단순화) ⑤ 스캐폴드: 폴더 트리 · 시그니처만 있는 빈 파일 · 모듈별 계약 테스트가 **빨강으로 도는 것을 실행해 확인** · 통합 테스트 1개 · 자를 순서와 구현 끝까지 예상 시간이 남은 시간 안 ⑥ 방향·버린 후보·설계 변경마다 `decision`, 구현 직전 평가(`docs/judge/모드1-*.md`) 지적을 전부 처분(수용은 고침 · 기각은 이유 · 실무자 확인은 설계 DM 으로) — 평가를 버리기 사다리로 건너뛰었으면 그 `decision` 으로 대신한다.
- **피드백 관문** (M4 피드백 DM — `docs/interview/M4.md`, 반영처 `docs/FEEDBACK.md`) — 구조는 위 원리와 같다. 다 차면 「피드백 끝내도 됩니다」를 권한다.
  - ㉠ 꼭 받기 3개: ㉠1 성공 기준마다 달성·미달을 실무자가 인정(미달은 이유·조건 합의) · ㉠2 **수용 확인(④)** 에 명시 답 — 이번에 만든 것 / 안 만든 것과 이유 · ㉠3 고친 것(버그·틀린 숫자 전부)을 실무자에게 **다시 보여 확인**받았다(숫자 포함)
  - ㉡ 물어보면 충족 3개: ㉡1 「어디서 멈추실지 · 빠진 것 · 틀린 숫자」를 물었다 · ㉡2 화면 흐름 묘사(아래 ③ 형식)와 결과물 원문을 보냈다 · ㉡3 남은 한계를 숨기지 않고 말했다(= README 「안 된다」)
  - 자체 점검 5개: ① FEEDBACK 1절 — 성공 기준마다 실제 데이터 결과 숫자와 측정 명령(출력이 있다) ② 답변 문장이 전부 F-ID 로 분류됐다(남은 문장 0) · 새 요구는 받지 않았으면 이유를 실무자에게 말하고 4절, 받았으면 사용자 결정과 PLAN 7절 자를 순서 조정 · 작은 보정은 MUST 안이면 고침, 밖이면 사용자 판단을 `decision` ③ 처분마다 `decision` · PLAN 2절 상태 · README 「된다/안 된다」 반영 ④ **독립 재계산** 일치(`guides/STAGES/M4-피드백.md`) ⑤ 고친 뒤 통합 테스트와 `./verify.sh` 전체 PASS · `python3 tools/security_check.py` 막는 것 0
- **숨은 사실 점검표**(문제 관문 ㉠3 의 일부 — `요약.md` 에 칸이 있다): 단위 · 중복 · 시간대 · 제외 대상 · 분류 기준 · 빈 값 의미 · AI 사용/외부 전송(과제 API 가 제공돼도 제품 AI 를 넣을지는 실무자에게 묻는다 — 답변 번호를 적는다) · 개인정보를 **DM 에서 다 확인했나** 각각 「확인됨(답변N) / 아직」으로 표시한다. 「아직」은 DM 에서 묻고, 답이 「모른다」면 ㉢ 로 닫아 「가정(D번호)」로 바꾼다. 「아직」이 남으면 오케는 「문제 확정」 때 그 줄을 먼저 보인다. 실무자가 「확인해 봐야 해요」라고 하면 데이터로 먼저 결정하고 근거(건수 · 예시 행)를 보이며 재확인한다(미답을 곧 보류로 확대하지 않는다 — F1 의 최대 감점 원인). **보류·미분류·제외 비율이 10% 를 넘으면 경고하고 목록 일부를 보이며 실무자에게 묻는다.**
- **첫 질문**(「DM 시작하자」): 오프닝 + PROBLEM 15절 맨 위(브리핑 ⑤에서 나온 가장 깊은 좌표) 질문 2~3개(최근 에피소드 · 앞 구간 · 말하지 않은 것 하나)를 한 묶음으로. 해법 단어 금지.
- **메모는 정답지가 아니다**: 오케스트레이터는 `docs/MEMO.md` 를 읽지 않는다. 사용자가 메모를 붙여 넣으면 가설 입력으로만 받는다 — README·데이터·실무자 답과 어긋나면 근거를 들어 짚고, 메모를 따르기 위해 사실을 굽히지 않는다.

## ⓪ 오프닝 (역할극 — 첫 메시지)

상대는 실무자 role-play 중이다. 나도 파견 나온 FDE로서 말한다 — 완곡하고 존중하되, 목적은 분명하게:

> "안녕하세요, 이번 과제를 맡은 개발 담당입니다. 보통이라면 제가 현장에 며칠 함께 있으면서 실무자님 일하시는 걸 옆에서 봤겠지만, 오늘은 여건상 이 대화로 파악해야 하는 점 양해 부탁드립니다. 제가 알고 싶은 건 **실무자님의 하루에서 무엇이 가장 시간을 잡아먹는지**입니다. 구체적으로 답해주실수록 정확한 도구를 만들어 드릴 수 있습니다."

- 상대가 쓰는 **용어를 그대로 따라 쓴다**(그 용어가 리서치 검색어가 된다).
- 첫 3분 해법 단어 금지는 여기서도 유효 — 오프닝에 "자동화·대시보드·AI" 안 넣는다.

### 턴 예산 2시나리오 (제한 여부 미확정 — DM 패널에 "컨텍스트: N개 메시지" 카운트가 뜬다)

- **무한정으로 보이면**: 현행대로 — 짧은 질문 여러 번.
- **제한이 의심되면**: 1턴에 [에피소드 + 빈도·소요시간 + 측정처]를 한 묶음으로 묻고, 합의문(②)을 조기에 보내 정정 기회로 쓴다. 마지막 턴 근처엔 "지금까지 제가 이해한 것 중 제일 크게 고칠 부분 하나만 짚어주세요."

## ① 발굴 (코드 작성 전)

- **에피소드**: "가장 최근에 그 일이 있었던 때를 구체적으로 알려주실 수 있나요? 그때 무엇을 하셨나요?"
- **워크어라운드**: "지금은 그걸 어떻게 처리하고 계세요? 그 방식의 제일 아쉬운 점은요?"
- **정량화**: "얼마나 자주 있는 일인가요? 한 번에 시간이 얼마나 들어가나요?"
- **당사자**: "이게 제일 아쉬운 분이 누구세요? 그분 입장에서 뭐가 달라지면 성공인가요?"
- **경계**: "반대로, 건드리면 안 되는 것·꼭 지금처럼 남아야 하는 흐름이 있나요?"
- **시간 되짚기**: 에피소드를 들으면 순서를 거슬러 묻는다 — "그 정보는 **언제 어디로** 왔나요?", "왜 하필 그때 하셨어요?" (병목이 능력이 아니라 **정보 도착 시점**인 경우가 많다)
- **측정처 확인**: 숫자가 나오면 "그건 지금 **어디에 기록**되나요?" — 아무도 안 세는 지표는 성공 기준이 될 수 없다.
- **사례 근거 질문**(`docs/research/현장사례-*.md` 에서): 다른 현장에서 실제로 터진 문제를 근거로 **에피소드를 묻는다**. 예/아니오 유도형(「이런 문제를 겪고 있진 않으세요?」)은 금지 — 상대는 웬만하면 「네」라고 한다. 좋은 예: 「비슷한 현장에서는 월말 마감 때 같은 건이 두 번 잡히는 일이 있다고 하던데요, 여기서는 가장 최근 마감 때 어떻게 처리하셨어요?」 답이 「그런 일 없어요」면 그것도 사실로 기록하고 사례는 버린다. 사례는 실무자가 확인하기 전까지 PROBLEM 15절·STRATEGY 3 에만 둔다.
- 듣기 규칙: 답변에서 **요구와 원인을 분리해 되말하기**("~가 불편해서 ~를 원하시는 거군요, 맞나요?").

### 발굴 단계 금지 4 (훈련에서 반복 적발된 실패)

1. **해법 단어 금지** — 첫 3분은 질문만. 화면·자동화·예측 같은 말을 내가 먼저 꺼내지 않는다. **상대는 웬만하면 "네 좋아요"라고 한다** — 그 동의는 검증이 아니라 함정이다.
2. **상대가 자진 공개한 것에 만족 금지** — 핵심 원인을 상대가 먼저 말해줬다면 그건 캐낸 게 아니다. 한 겹 더 판다.
3. **기준선 없는 숫자 금지** — "절반으로", "3분의 1로"는 무엇 대비인지 없으면 합의가 아니다. 상대가 실제로 세는 숫자 + 현재 값을 함께 적는다.
4. **정정을 흘려듣기 금지** — 되말하기에 상대가 "절반은 맞는데요"로 답하면 그 자리에서 문제 정의를 다시 쓴다.

### 행간 청취 — 말하지 않는 것을 듣는다

질문 목록만 돌리면 표면만 걷는다. 답변의 **바깥**을 듣는 동작 4개 (전부 리허설 1 실증):

1. **흘린 말 잡기** — 실무 제약은 요구사항이 아니라 부수적 발화에 섞여 나온다. 지나가는 숫자·기한·예외("아 그건 2주 지나면 처리해요")는 그 자리에서 되묻는다. (리허설: 흘린 한마디 2개가 설계를 바꿨다 — 물증 보관 기한이라는 두 번째 시계, 월 341건이라는 규모)
2. **안 하는 말 파기** — 답이 갑자기 짧아지는 주제, 스스로 안 꺼내는 영역(돈·실수·상급자 관계)이 pain의 좌표일 때가 많다. 직진하지 말고 우회로 — "그 부분은 보통 어떻게 처리되나요?"
3. **감정 신호 = 문제의 좌표** — 허탈·부끄러움·방어가 실린 문장이 나오면 그게 문제 정의의 중심 후보다. (리허설: 진짜 문제는 기능 요구가 아니라 "'기타'가 1등인 표를 올리면서 이게 무슨 의미가 있나 싶었다"는 감정 진술에서 나왔다)
4. **말 vs 데이터 대조** — 진술 숫자와 실측이 어긋나면(체감 "3할" vs 실측 30.9%) 지적하지 말고 질문으로 되돌린다. 어긋남 자체가 금맥이다 — 본인도 모르는 것을 같이 발견하는 지점이고, 그 발견이 신뢰를 만든다.

### 도메인 렌즈 — 경영학으로 캐는 질문 (남들이 못 파는 곳)

같은 병목도 경영 언어로 물으면 한 겹 더 들어간다. 대화에서 해당 축이 보이면 꺼낸다:

| 렌즈 | 질문 | 노리는 것 |
|---|---|---|
| **돈의 흐름** (재무·관리회계) | "그 일이 늦어지면 회사엔 뭐가 비싸지나요 — 사람 시간인가요, 놓친 매출인가요, 벌금·페널티인가요?" | pain을 손익 줄에 고정 → 성공 기준 숫자의 출처 |
| **병목·리드타임** (생산관리·제약이론) | "전체 흐름에서 가장 오래 **기다리는** 단계가 어디예요? 그 앞엔 일이 쌓여 있고 그 뒤는 놀고 있나요?" | 진짜 제약 식별 — 병목 앞 적체·뒤 유휴가 신호 |
| **고객 행동** (마케팅·소비자행동) | "그 문제가 생기면 최종 고객은 뭘 하나요 — 기다리나요, 이탈하나요, 문의를 넣나요?" | 내부 병목 → 고객 손실 연결 (임팩트 서사) |
| **의사결정 구조** (전략·조직) | "그건 최종적으로 누가 결정하고, 그분은 어떤 숫자를 보고 결정하나요?" | 결정 화면의 사용자·지표 확정 |
| **통제·감사** (회계·세무·상법·컴플라이언스) | "그 수치는 나중에 누가 검증하나요? 장부·신고·감사·정산·이사회 보고에 걸리는 지점인가요?" | 오류 비용이 규제 비용이면 우선순위 급상승 |
| **수요 변동** (운영·재고) | "바쁠 때와 한가할 때 차이가 큰가요? 제일 바쁜 날은 언제고 그날 뭐가 제일 먼저 무너지나요?" | 피크 기준 설계 — 평균으로 설계하면 피크에 깨진다 |

- 렌즈는 **한 번에 하나** — 심문이 아니라 대화다. 상대 답에서 다음 렌즈를 고른다.
- 렌즈로 얻은 숫자는 반드시 "그건 어디에 기록되나요?"로 측정처까지 붙인다.

## ② 서면 합의 (구현 착수 전 — 필수 관문)

다음 형식으로 보내 **명시적 확인**을 받는다. 확인 전 구현 착수 금지. **한 덩어리로 복사해 갈 수 있는 형태**여야 한다 — 상대가 자기 상급자에게 그대로 공유할 수 있어야 합의다(대화 여러 줄에 흩어진 구두 동의는 합의가 아니다).

```
■ 제가 이해한 문제
  (표면 요구가 아니라 원인으로 — 한 문장)

■ 왜 생기나 (병목)
  (언제·어디서 막히는지)

■ 성공 기준  ※ 숫자 + 지금 값 + 어디서 재는지
  ① <지표> : 현재 <값> → 목표 <값>  (측정처: <시스템·파일>)
  ② <지표> : 현재 <값> → 목표 <값>  (측정처: <시스템·파일>)

■ 이번에 만들 것 / 안 만들 것
  만든다: …
  안 만든다: … (이유: 시간·범위)

■ 제약 (못 바꾸는 것)
  …

이대로 맞을까요? 다르면 고쳐 주세요.
```

**빠르게 채우는 법** — 대화가 길어 기억이 안 나면 위 골격을 그대로 붙여넣고 이렇게 시킨다:

```
지금까지의 대화 전체를 근거로 위 합의문 골격을 채워라.
- 대화에 실제로 나온 말만 쓴다. 없는 숫자·측정처를 지어내지 마라.
- 상대가 정정한 내용이 있으면 정정된 쪽을 쓴다.
- 근거가 없는 칸은 비워두고 "미확인"이라 표시해, 내가 물어볼 수 있게 하라.
```
→ 출력에 「미확인」이 남아 있으면 **그것부터 상대에게 물어본 뒤** 보낸다.

합의 내용과 시각을 `AGENTS.md` 「목표 · 컨텍스트」와 `docs/interview/요약.md` 「합의」에 기록.

## ③ 중간 검증 (동작하는 최소본이 나온 직후)

- 실무자는 **텍스트만** 본다(이미지·링크를 열 수 없다고 가정 — 사전 체험에서 확인). 그래서 화면을 **묘사 문구**로 보낸다:
  1. 첫 화면 위→아래로 보이는 것(제목 · 요약 숫자 · 목록의 첫 3줄을 실제 값 그대로)
  2. 반장님이 누르는 순서대로 무엇이 바뀌나(「장비를 EQP-104 로 고르면 목록이 5줄로 줄고 위 숫자가 …로 바뀝니다」)
  3. 내려받는 결과물 원문을 그대로 붙인다(메모·리포트의 앞 10줄)
  4. 질문은 「이 순서로 쓰실 때 어디서 멈추실 것 같나요?」「3번 메모에서 빠진 게 있나요?」처럼 묘사한 부분을 짚는다
- 피드백을 반영/보류로 나누고, 보류엔 이유를 남긴다(`docs/DECISIONS.md`).

## ④ 수용 확인 (M4 피드백 마지막 턴 — M5 에 따로 DM 하지 않는다)

- 합의한 성공 기준을 하나씩 대조해 보고: "①은 이렇게 확인됩니다. ②는 여기까지만 됐고 남은 건 ~입니다."
- 미충족을 숨기지 않는다 — 남은 일과 조건을 명시하는 것까지가 완결이다.
