# 작업 위임·재지시·수신

구현 세션은 대화 전체를 모른다. **브리프 한 장만 읽고 시작할 수 있어야** 한다. 사용자는 새 터미널 탭에서 `codex` → `/model` 가벼움 등급 · medium(경계 복잡하면 표준 등급 — `guides/KICKOFF.md` 세션 편성 표) → 「`docs/mail/<모듈>.md` 읽고 그대로 해」 한 줄만 친다.

## 발행 (최초 계약 40줄 이내, 이후 메시지는 끝에 추가)

```
# 브리프 — <모듈> (발행 <HH:MM>, 마감 <HH:MM>)
## 원인·범위
기존 편지함이 있으면 마지막 메시지·인계 요약부터 읽고 중복 위임하지 않는다.
<왜 이 모듈이 필요한가 한 줄> · 폴더 `src/<모듈>/`·`tests/<모듈>/` 밖은 고치지 않는다.
## 입력 → 출력 (공개 인터페이스)
<함수·파일·형식 — 호출하는 쪽이 의지하는 것만>
## 지킬 것
- **요구에 없는 기능은 만들지 않는다**(PLAN 2절 요구 ID 에 없는 것은 만들지 않고 concerns 에). 오버엔지니어링 금지.
- 결정론 코어: 판정·집계는 규칙 코드 + 테스트. AI 호출이 있으면 고정 폴백.
- 테스트에 **이상 입력·경계값 테스트 최소 3개**(빈 입력 · 형식 틀림 · 경계 날짜/값) — 정상 경로만 테스트하지 않는다. 테스트 이름에 PROBLEM 9절 요구 ID(`test_r1_…`)
- 데이터 처리 규칙(PROBLEM.md 4·5절·DECISIONS 에서 해당 줄 복사)
- 데이터 계약·규칙 파일·오류 처리(`docs/ARCHITECTURE.md` 7·8·10절에서 이 모듈 줄 복사) — 규칙 값은 코드에 박지 않고 규칙 파일에서 읽는다
- 보안: 10절 7항목 중 이 모듈 줄 · 입력 검증 테스트 1개 이상(형식 오류·초대형·경로 조작 중 해당) · 시크릿은 `.env` 로만 · 설계에 없는 외부 요청 금지
- <바꾸면 안 되는 동작·파일>
## 완료 조건 (pass/fail)
- `./verify.sh "<테스트 명령>"` PASS — 테스트 파일 `tests/<모듈>/...` 에 <단언 한 줄>
- 실패 → `.agents/skills/systematic-debugging/SKILL.md`의 재현·원인 확인 → 최소 수정 → 같은 명령 재통과. 같은 원인으로 2번 실패면 멈추고 보고.
- 계약 테스트 `tests/contract/` 는 고치지 않는다(오케스트레이터 소유). 틀렸다고 보면 concerns 에.
- `src/<모듈>/README.md` 를 `starter/README-TEMPLATE.md` 맨 아래 「모듈 README 틀」로 — 명령은 실제로 돈 것, 파일·함수 이름은 실제로 있는 것만
## 끝나면
`git add src/<모듈> tests/<모듈> docs/mail/<모듈>.md && git commit -m "<모듈>: <무엇>" -m "<왜>"` → mail.md 형식의 완료 답장에 아래 보고 4줄과 결과 커밋을 붙이고 오케에게 queue 알림을 보낸다 → 마지막 줄은 눈에 띄는 고정 형식 `■ 완료 — 오케스트레이터에: <모듈> 끝 · 이 탭: 열어 둠(M4 끝까지 재지시용)` (사람이 탭을 훑다가 ■ 만 찾는다).
status / changed(파일) / verification(빨강 출력 → 초록 출력) / concerns(결정 필요한 것)
## 재지시 (오케스트레이터가 검수 뒤 필요할 때만 맨 아래에 붙인다)
<빠진 것·고칠 것> — 파일 저장 뒤 queue로 알린다. 실패한 경우만 사람에게 그 탭에 「편지함 확인해」를 요청한다. 같은 지적으로 2번 실패하면 새 탭.
```

- **지시 전에 검증 방법 먼저**: 완료 조건의 실행 가능한 명령을 브리프에 먼저 쓰고 나서 구현 지시를 쓴다. **같은 원인으로 2번 실패하면 멈추고 지시(브리프)를 고쳐 다시 보낸다** — 같은 말을 되풀이하지 않는다.
- 한 브리프 = 한 모듈 = 한 세션. 예상 소요를 머리에 적는다(응답 대기 시간 포함).
- 브리프의 완료 조건에는 `docs/PLAN.md` 2절 요구 추적 표에서 그 모듈이 맡은 요구 ID · 테스트 이름 · 검증 명령과 4절 데이터 처리 규칙을 그대로 옮긴다. 브리프를 쓰면 `docs/PLAN.md` 6절 모듈 표의 「브리프·상태」를 갱신하고 「위임 장부」에 행을 열고(맡기기 전에 장부를 봐서 같은 일이 이미 다른 탭에 있지 않은지 확인), 사용자에게 「탭 열고 이 경로」 한 줄을 말한다.

## 수신

1. queue 알림 또는 사용자가 「`<모듈>` 끝」이라고 전하면 그 브리프 파일을 읽는다. 끝나는 순서대로 받는다. 검증 명령·기대·실제·종료코드가 없으면 되돌려 보낸다. 실제 실패가 없었다면 빨강 기록을 만들려고 코드를 망가뜨리지 않는다.
2. 검수 4 — ① 완료 조건 명령을 **직접** `./verify.sh` 로 재실행(계약 테스트 초록, PASS 아니면 받지 않음) ② `docs/ARCHITECTURE.md` 모듈 표·브리프 「지킬 것」과 대조 + `src/<모듈>/README.md` 가 있고 그 검증 명령이 실제로 돈다 + `python3 tools/security_check.py` 막는 것 0 ③ 보고한 각 커밋을 검사하고 타 워커 커밋을 섞지 않는다: `git diff-tree --no-commit-id --name-only -r <워커가 보고한 각 커밋> -- . ':!src/<모듈>' ':!tests/<모듈>' ':!docs/mail/<모듈>.md'` 로 범위 밖 변경 0 ④ `tests/contract/` 무변경(바뀌었으면 즉시 불합격). 빠진 것은 브리프 맨 아래 「재지시」 절로 돌려보낸다.
3. `docs/PLAN.md` 「위임 장부」의 그 행에 실제 소요와 결과(통과 / 재작업 N)를 채운다. 통과하면 브리프 맨 아래에 `검수 <HH:MM> 통과 — verify PASS` 한 줄 → 자기 검수 기록 경로만 stage 후 `git commit -m "review: <모듈> 통과"` — 커밋 트리거 4.
4. 새 구조가 들어왔으면 사용자에게 3줄 브리핑하고, 약점이 보이면 `docs/QNA.md` 에 한 줄. PLAN 상태를 「완료」로.

## 화면 모듈 브리프에 반드시 옮길 계약

- 먼저 `guides/DESIGN.md`와 `starter/DOMAIN.md`, `starter/shadcn/INTEGRATION.md`를 읽는다. 구현할 탭에서 `command -v node; node --version`을 확인한다(오케 탭의 버전으로 대체 금지).
- 새 화면 기본은 `bash starter/shadcn/make.sh <제품 폴더>`. 실패하면 오류를 보고하고 준비된 `starter/shell/`을 쓴다. 별도 HTML을 새로 만드는 우회는 하지 않는다. 과제 제공 앱이 있으면 기존 앱을 우선하고 선택 이유를 기록한다.
- 생성된 App·라우팅·페이지·위젯을 먼저 읽고 유지한다. 도메인 설정·데이터 연결·필요한 기능만 수정한다. App.tsx를 삭제하고 전체 화면을 다시 쓰지 않는다. 기존 구조로 요구를 충족할 수 없으면 근거와 변경 범위를 먼저 오케에 보고한다.
- 완료 조건: 실제 데이터 연결 + 빌드 통과 + Browser에서 `guides/img/shadcn-recipe-sk.png`와 기본 레이아웃 대조. 사용한 페이지·위젯과 바꾼 파일을 보고한다. 빌드 성공만으로 준비 UI 재사용을 충족 처리하지 않는다.
## 편지함으로 발행

최초 계약 위에 상대 역할·작업 ID·오케의 세션 ID·워커 세션 ID(처음엔 미등록)·읽을 역할 문서·전용 스킬·산출물 경로를 적는다. 식별·등록·메시지 형식은 [mail.md](mail.md). 최초 기동 문장: `AGENTS.md와 .agents/skills/handoff/SKILL.md를 읽고 docs/mail/<역할-작업>.md의 미처리 지시를 수행해`.

고정 역할(평가·보안·제출점검·DM·설명)도 편지함을 받을 수 있다. 각 역할의 전용 스킬과 결과물 위치를 최초 계약에 연결한다. 평가·보안·점검의 읽기 전용 계약과 결과 문서 소유를 유지한다. 서브에이전트로 이미 실행 중이면 새 탭에 중복 발행하지 않는다.

재지시는 이전 완료 메시지 ID에 회신으로 추가한다. 워커가 실행 중이면 같은 지시를 덮어쓰지 말고 다음 메시지로 큐에 둔다. 범위 변경은 오케가 계약 변경 메시지로 명시하고 필요하면 사용자 판단을 받는다. 완료 답장 후 대기, 오케의 수락/재지시를 받으면 다음 행동을 한다.

- 화면 위임 계약에는 데이터 입력 경로·필드 매핑·기준일/단위·판정 결과 책임·저장 API·빈 데이터/오류 기대 화면을 명시한다. 결과 API 실패를 샘플로 감추지 않는다. Browser는 `http://localhost:3000/` 링크로 확인한다.
