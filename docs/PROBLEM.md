# PROBLEM.md — 문제 정의서 (살아 있는 문서)

> 「과제 브리핑해줘」 때 README·데이터로 첫판을 쓰고, **실무자 답이 올 때마다 고친다.** 확정은 「문제 확정」 때. 확정 시각: (    )
> **출처 태그 — 모든 줄 끝에 하나**: `[README:줄]` `[데이터 파일:행]` `[답변N]` `[사용자]` `[짐작]`. `[짐작]` 은 인터뷰로 확인되기 전까지 설계 근거로 쓰지 않는다.
> **바뀐 줄은 지우지 않는다** — `~~옛 내용~~ → 새 내용 [답변N]`. 가설이 어떻게 바뀌었는지가 서술형 재료다.
> 갱신 이력: (HH:MM 답변N — 바뀐 절 번호)

> 기계 점검: `python3 tools/problem_check.py` — 빈 절 · 출처 태그 없는 줄 · `[짐작]`(`[가정:D번호]` 가 붙으면 허용) · 1절 `[?]` · 숨은 사실 점검표 「아직」을 센다. 판단 항목은 `guides/INTERVIEW.md` 「문제 확정 관문」.
## 0. 한눈에 (브리핑 요약 — 갱신 때마다 다시 쓴다)
채우는 지침: 상황을 필요한 만큼(누가 · 무슨 일로 곤란한가 · 왜 지금인가 · 안 풀면 무엇이 비싼가). 줄 수 제한 없음. 맨 끝에 「지금 가장 큰 미확인 1개」.
-

## 1. 일의 흐름 — 처음부터 끝까지
채우는 지침: 입력이 어디서 오나 → … → 결과를 누가 받아 다음에 무엇을 하나, 화살표 한 줄. README 가 비운 구간은 `[?]` 로 표시하고 15절로 보낸다. 가장 오래 **기다리는** 단계에 ⏳.
-

## 2. 걸린 사람
채우는 지침: README 에 이름이 없어도 이 일에 걸린 사람(결재자·하류 수신자·감사·고객)까지 꼽는다. 「말하지 않은 요구」는 근거(답변·데이터·업무 상식)를 붙이고, 근거가 없으면 `[짐작]`.

| 사람 | 하는 일 | 말한 요구 | 말하지 않은 요구 (근거) | 결과를 받아 다음에 하는 일 | 감정 신호·흘린 말 |
|---|---|---|---|---|---|

## 3. 표면 요구 vs 진짜 문제
채우는 지침: 「~가 불편해서 ~를 원한다」로 요구와 원인을 가른다. 실무자 되말하기에 「네 그거예요」가 나오기 전엔 가설이다. 「절반은 맞는데요」면 그 자리에서 다시 쓴다.
-

## 4. 업무 규칙과 예외
채우는 지침: 판정·계산·마감·우선순위 규칙을 한 줄씩. **흘린 말의 숫자·기한·예외**(「그건 2주 지나면 처리해요」)는 전부 여기. 이 줄들이 결정론 코어와 테스트가 된다 — 규칙마다 테스트로 바꿀 수 있는 문장으로.
-

## 5. 데이터 원천과 한계
채우는 지침: 파일·열·행 수·기간, 결측·중복·단위·ID·기간 경계 의심 지점(코드로 점검, 근거 `파일:행`). **실무자 말과 데이터가 어긋나는 곳**은 따로 표시 — 지적하지 말고 질문으로 되돌린다.
-

## 6. 용어집
채우는 지침: 실무자가 쓴 말 그대로 → 뜻 → 대응하는 데이터 열·코드 이름. 질문 글·화면 문구·서술형 답에 이 말을 쓴다.
| 실무자 용어 | 뜻 | 데이터 열·코드 이름 | 출처 |
|---|---|---|---|

## 7. 목표 한 문장
채우는 지침: 만들 것이 아니라 바뀌어야 할 상태.
-

## 8. 성공 기준 (pass/fail)
채우는 지침: 지표 · 지금 값(기준선) → 목표 값 · 어디서 재나. 아무도 안 세는 지표는 성공 기준이 아니다.
-

## 9. 요구 표
채우는 지침: README 요구 + 인터뷰에서 나온 요구. MUST 를 전부 닫기 전엔 선택을 시작하지 않는다. **행마다 ID(R1·R2…)를 달고**, 브리프 완료 조건·테스트 이름(`test_r1_…`)·README 「된다」 표 행이 같은 ID 를 쓴다.
| ID | 요구 | MUST/선택 | 근거 | 상태 (README 만 · 실무자 확인 · 실무자 정정) |
|---|---|---|---|---|
| R1 | | | | |

## 10. 하지 않을 것과 이유
채우는 지침: 기각마다 이유(시간·데이터·제약·위험). 이유 없는 제외는 누락이다.
-

## 11. 제출 조건
채우는 지침: 필수 파일명·형식·실행 방법·평가 방식을 README 근거 줄과 함께. 제출 점검 탭이 이 절로 확인한다.
-

## 12. 제약
채우는 지침: 못 바꾸는 것 — 시간 앵커, 도구·환경(recon 한 줄), 데이터 사용 범위, 현장에서 지금처럼 남아야 하는 흐름.
-

## 13. 리스크
채우는 지침: 터지면 무엇이 깨지나 + 먼저 확인할 방법. 약점은 `docs/QNA.md` 에도 한 줄.
-

## 14. 모퉁이 너머
채우는 지침: 결과가 나온 뒤 — 2차 효과, 운영 중 깨지는 지점, 인수인계, 다음 달에 묻게 될 것. 2~3개, 각각 지금 막을 수 있는지.
-

## 15. 미확인과 다음 질문 후보
채우는 지침: 모르는 것은 지어내지 않고 여기에. 「답이 오면 무엇이 바뀌나」(절 번호·결정)가 큰 것부터 위로. 다음 DM 질문은 이 표 맨 위에서 고른다.
