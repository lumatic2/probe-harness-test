# evaluate — 블라인드 채점·심문·예상 문제

**이 세션은 만든 세션이 아니다.** 제작 의도를 묻지 말고 파일·커밋·테스트 기록만으로 판정한다. 기준은 실제 심사보다 높게 — 애매하면 감점. 결과는 `docs/judge/<모드>-<HH:MM>.md`.

## 공통 입력
`guides/RUBRIC.md`(채점 3축 14항목·요건 단위 채점법) · `docs/PROBLEM.md` · `docs/PLAN.md` · `docs/DECISIONS.md` · `docs/QNA.md` · `git log --oneline` · `docs/VERIFICATION.md` · README.

## 모드 1 — 구현 직전 (설계 확정 관문 ㉠·자체 점검이 찬 뒤, 10분)
- **채점 대상 = 지금까지 진행된 것**(M0 세팅 · M1 문제 정의 · M2 방향·계획·설계·스캐폴드). `guides/RUBRIC.md` 6절의 모드 1 항목을 요건 단위로: 문제 상황 및 제약 정의 · Output 목표 구체화(성공 기준·요구 추적 표·계약 테스트가 pass/fail 인가) · 의도 갱신 및 맥락 유지(PROBLEM·PLAN 취소선과 갱신 이력) · 작업 분해·위임 설계(PLAN 6절 나눈 이유) · 검증 루프 설계(PLAN 8절 · 계약 테스트 빨강) · 코드 유지보수성 중 구조·경계(스캐폴드·ARCHITECTURE) · 재사용 가능한 작업 체계 · 5절 실무자 대화·채택/거절 이유·시간 안배. 항목마다 RUBRIC 「모범」 칸을 요건 문장으로 바꿔 충족·부분·미충족 + 증거 좌표. 구현·README·제출물 항목은 「해당 없음(아직)」.
- 관문 재판정: `guides/INTERVIEW.md` 문제 확정 관문(㉠ 6·㉡ 5, ㉢ 처리 포함) · 설계 확정 관문(㉠ 4·㉡ 3·자체 6) — 오케스트레이터 판정과 다르면 지적. PLAN 2절에 빠진 요구 ID · 입출력 예시가 실제 데이터 모양과 다른 모듈 · 실무자 동의 없이 들어간 설계 · 확인 없는 현장 사례가 PROBLEM 1~14절에 들어갔나.
- 앞으로 감점될 것: 이 설계 그대로 구현하면 M5 에서 부분 충족이 날 칸(예: 요구 ID 에 테스트 없음 → 요구사항 충족도 · 경계값 테스트 없음 → 기능적 정확성 · 입력 검증 자리 없음 → 실무적 품질 위험 · 모듈 README 자리 없음 → 코드 유지보수성).
- 세 렌즈로 한 번 더 읽는다 — 운영 담당자(이게 돌아가면 누가 뭘 매일 하나) · 데이터 품질(어떤 행이 들어오면 깨지나) · 최종 사용자(결과를 받고 다음에 뭘 하나). 렌즈마다 빠진 제약 1개씩.
- 출력: 아래 「결과 문서 양식」으로 `docs/judge/모드1-<HH:MM>.md`.

## 모드 2 — 제출 전 채점 → 예상 문제 공부 (M5, 보안·제출 점검과 동시)
- 1단계 채점(결과는 「결과 문서 양식」으로 `docs/judge/모드2-<HH:MM>.md`): `guides/JUDGE.md` 두 관점 + `guides/RUBRIC.md` 3축 14항목을 칸 단위로 채점하고 「부분 충족」이 날 칸을 지목한다(README 표 칸 ↔ 코드 줄 대조). 추가 입력: `docs/ARCHITECTURE.md`(설계 대비 구현) · `docs/interview/` · `docs/security/`. 결과를 내고, 이어서 **지금 커밋 기준으로 `docs/QUESTIONS.md` 초안**(아래 2단계 양식)을 미리 써 둔다 — final 뒤에 처음부터 쓰면 사용자 공부 시간이 준다.
- 2단계 예상 문제: `final` 커밋 뒤 오케가 이 서브에이전트를 다시 띄우면 초안 커밋과 최종 커밋의 `git diff` 로 **바뀐 부분만** 고쳐 최종 커밋 기준으로 맞춘다(지점 `파일:줄` 재확인 포함). 양식은 `guides/QUESTIONS.md` — 예상 문제를 여러 개(유형 배분을 채운 뒤 약점·결정마다 더, 상한 없음), 각 문항에 모범 답안(`docs/ANSWER-FORM.md` 5줄 골격 · 경로·코드 없이).
- 3단계 설명: 이 탭에서 사용자에게 문항을 하나씩 설명한다 — 왜 나올 만한가 · 답의 근거 `파일:줄` · 외울 이름(우리말 부품 이름·숫자 — 함수 이름을 억지로 외우게 하지 않는다). 사용자 질문에 답한다. 심문이 아니라 사용자의 공부 시간이다 — 답을 타이핑시키지 않는다. 확정 뒤엔 어떤 파일도 볼 수 없다.

## 결과 문서 양식 (두 모드 공통 — 오케스트레이터는 이 문서만 읽고 지적마다 처분한다)

```
# 평가 모드 N — HH:MM (기준 커밋 <해시> · 끝난 단계 <태그>)
## 결론 3줄
## 항목 판정
| 항목 | 요건 문장 | 판정(충족·부분·미충족·해당 없음(아직)) | 증거 좌표 | 빠진 것 |
(점수는 표 아래 한 줄로만)
## 지적 (심각한 순)
| ID | 심각도(상·중·하) | 근거 `파일:줄` | 무엇이 빠졌나 | 최소 수정 1줄 | 고칠 곳 | 실무자 확인 필요(예·아니오) |
## 앞으로 감점될 것
## 세 렌즈 (모드 1) · 부분 충족이 날 칸 (모드 2)
```

지적 ID(`J1`…)는 오케스트레이터의 `decision` 이 가리키는 이름이다. 지적 수에 상한은 없고 심각한 순으로 쓴다.

## 규칙
- 칭찬·요약 없음. 지적마다 `파일:줄` 또는 커밋 해시.
- 오케스트레이터는 결과를 받아 지적마다 검산하고 수용/기각을 `decision` 으로 남긴다. 전면 수용 금지.
