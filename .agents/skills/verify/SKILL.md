# verify — 같은 커맨드로 재통과

1. 커맨드: 사용자가 준 것, 없으면 `AGENTS.md` 「목표 · 컨텍스트」의 검증 커맨드. 둘 다 없으면 묻는다.
2. `./verify.sh "<커맨드>"` 로 실행한다(기록은 스크립트가 `docs/VERIFICATION.md` 에 한다).
3. 결과별:
   - **PASS(0)** → 응집 변경 1개를 `git commit`(제목=무엇, 본문 한 줄=왜) — 커밋 트리거 3. 그 뒤 한 줄 보고로 끝.
   - **NOVERIFY(2)** → 통과가 아니다. 테스트가 0개 돌았거나 커맨드가 비었다. 검증 대상을 찾아 커맨드를 고치거나 테스트를 먼저 쓴다.
   - **FAIL(1)** → 원인 진단 → 최소 수정 → **정확히 같은 커맨드로** 재실행. 3회 실패하면 멈추고 진단 요약과 선택지를 사용자에게.
4. 버그를 고칠 때는 고치기 전에 그 버그를 잡는 테스트를 먼저 써서 FAIL 을 기록에 남긴 뒤 재통과시킨다(실패→수정→재통과가 채점 표면이다).
5. 수정이 설계를 바꾸면 커밋 전에 `decision` 스킬. 커밋 메시지 본문에 검증 결과 한 줄.
6. **독립 재계산**(M4 끝, `feedback` 커밋 전 — `guides/STAGES/M4-피드백.md`): 구현 코드와 별개로 **원본 데이터에서 핵심 숫자 3~5개를 새로 센다**(맥락 없는 서브에이전트 또는 짧은 스크립트 — 구현 경로는 보여 주지 않는다). 구현 결과와 대조해 `docs/VERIFICATION.md` 에 숫자 · 명령 · 일치/불일치를 남기고, 어긋나면 고쳐 같은 대조를 재통과시킨다. 같은 AI 에게 같은 코드를 다시 돌리게 하는 것은 검증이 아니다.
7. 위임 결과의 「완료했다」 보고는 이 절차를 직접 돌리기 전에는 받아들이지 않는다.

## 완료 주장과 증거의 범위
현재 변경 뒤 검증을 새로 실행하고 전체 출력·종료코드·실행 테스트 수를 확인한다. 빌드 통과는 기능 정확성이나 요구 충족을 증명하지 않는다. 보고에는 검증한 주장과 미검증 범위를 나눠 쓴다. 실패 이력을 만들기 위해 정상 코드를 일부러 깨뜨리지 않는다.
